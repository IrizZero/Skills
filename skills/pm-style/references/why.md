# Why each rule exists

The evidence behind the rules, without project detail.
Sources: a module built in PM style over several weeks in October and November 2026 (project A), and a proof of concept run from 10 to 19 November 2026 with 78 logged lessons and one cost count (project B).
Add one line per new or changed rule at each close-out.

## The hard rules

| Rule | What taught it |
|---|---|
| The PM decides, it does not do | Project B, cost count: the PM alone was a quarter of a round's cost and 43 percent with its own readers. About half of the PM's cost was hands-on testing. 74 percent fell while its context was above 300,000 tokens. |
| Scope check at every gate | Project B: the owner asked for a graph. The PM added an alarm, its calibration and its blind tests, one natural step at a time. Most of two days, removed by the owner in one message. The same slip returned twice as designing a future goal and as an over-sized proof. |
| Look before you design | Project B: a stage briefed before the first real file arrived cost an extra session. A two-round debate was held about a map nobody had opened; it held nothing usable. A list of speed-ups written before measuring had two of five wrong and missed two of the three largest. |
| Measured or carried | Project B: speeds and height written into a spec from memory were true for one input of three. An accuracy measured on a round trip was quoted for a one-way use where it was two to four times worse. A threshold learned on made-up data was useless within five minutes on real data. |
| Ask which input is fair | Project B: the first input downloaded, the hardest one, was the base of three stages. The owner found the fairer pair by looking at all three once. |
| The tester is not the builder | Project B: a blind test passed ten of ten using the generator the tool was designed against. An independent test, asked for by the owner, found the real weakness. |
| Size the proof to the stage | Project B: twelve runs of about fifty minutes were planned for one setting; the owner cut them to ten minutes after they had started. |
| No prediction as fact | Project B: "this runs into tomorrow" took 32 minutes. "One cause left" met two new ones. A tool's limit was used as a reason to leave data out that the owner wanted. |
| One writer, at most 3 sessions | Project A, and an earlier burst of seven parallel sessions that spent tokens for little. |
| Stop rule in every brief | Project B: a session that stopped at a failed requirement and tuned nothing made the failure usable, twice. |

## Briefs, messages and sessions

| Rule | What taught it |
|---|---|
| Must-do items go in the brief | Projects A and B: messages to a working session were read after the point they were meant for. Once this cost a whole extra session. |
| One fresh session per large stage, two planned for a stage that may grow | Project B: a first stage filled half a session's window; two later stages stopped half done and each needed another owner turn. |
| Builder lists acceptance lines it cannot meet | Project B: this caught a real spec fault before any code. |
| Report sections "noticed" and "what I could not check" | Project B: "noticed" twice found the best evidence of the project. A builder's own browser check found six defects that no test found. |
| Count the stop clock back from the after-run steps | Project B: a long run ended minutes after its clock, with no time for its checks, and stayed unfinished. |

## Gates and tests

| Rule | What taught it |
|---|---|
| Proofs as checkable files | Project B: a gate became one comparison of hashes, where earlier gates had been the PM's own re-runs. |
| One cold review per round by another model family | Project B: it found a scoring rule that five build sessions and the PM had all treated as settled. |
| Ask how strict a match is | Same review: "found N of M" had been reported for two days on a rule where one shared pixel counted. |
| Read where a score has its values | Project B: a check printed "met" from six edge samples while the curve had no value where it mattered. |
| Debate with a look in between | Project B: reading fifty lines of code between two rounds settled what argument had not. |

## Talking to the owner, bookkeeping, cost

| Rule | What taught it |
|---|---|
| Report only at gates, 150 words, one decision | Project B: seven status reports got no reply, each on a very large context. Side questions inside long reports went unanswered. |
| One state page, rewritten, one fact in one place | Project B: one PM session made 73 writes and 32 commits; one result stood in five places. |
| The lessons file holds lessons only | Project B: the file grew past 200,000 characters, under a third of it lessons, and the rules stopped being updated from it. |
| Hand over at a gate past half the window | Projects A and B: the owner's standing rule, and the cost count above. |
| Check commit messages when written | Project B: a message that broke an owner rule was found only at push time and cost a rewrite of eight commits. |
| Count the cost at the end of each round | Project B: the count was run once, late. The questions set for the end of the trial were never answered. |

## Learning

| Rule | What taught it |
|---|---|
| The owner approves each change to this skill | Decided by the owner on 2026-11-19. A PM that edits its own rules unchecked can write rules that excuse its mistakes. |
| A size budget | Project B: rules that grow without limit stop being read. |
